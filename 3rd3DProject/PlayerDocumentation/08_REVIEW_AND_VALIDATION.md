# 코드 검토와 검증 근거

## 현재 확인과 과거 기록을 읽는 기준

문서에 파일이 존재한다고 썼다는 것, 저장된 씬에 참조가 있다고 썼다는 것, 실제 플레이에서 성공했다는 것은 서로 다른 주장입니다. 이번 작업은 **기술문서 작성과 코드·연결 검토**입니다. 테스트 때문에 씬을 저장하거나 입력·메뉴·게임 상태를 바꾸지 않았습니다. 아래 과거 시험의 성공 개수를 이번 문서 작업에서 새로 통과한 개수로 해석하지 않습니다.

| 근거 종류 | 무엇을 확인할 수 있나요? | 확인할 수 없는 것 |
|---|---|---|
| 현재 C# 코드 | 조건, 호출 순서, 책임과 확장 지점 | 특정 PC에서의 실제 화면·프레임 타이밍 |
| 저장된 씬·프리팹·재질 | 연결과 직렬화된 값, 원본·변형 관계 | 편집기 미저장 상태, 실행 중 동적 값 |
| 기존 작업 로그 | 그 날짜에 수행했다고 기록된 변경과 시험 | 이후 수정이 같은 결과를 유지하는지 |
| 외부 시험 결과 파일 | 해당 시험의 실제 출력 | 로그가 다루지 않은 입력·환경 |
| 대화의 과거 요청 | 원했던 모양·기능과 승인 범위 | 원본 모델이나 코드가 없는 항목의 완료 여부 |

## 이번 문서에 적용한 정적 검토

기준 소스는 `6b8bafde`이며 Player의 C# 53개와 직접 연결된 Systems 10개를 색인에 포함했습니다. 소스 파일의 SHA-256, 줄 수, 선언된 타입, 저장된 대상 씬의 직접 참조를 [소스 스냅샷](evidence/source_snapshot.json)에 보관합니다. 해시는 파일 내용의 지문입니다. 팀원의 파일과 다르면 “같은 버전의 문서를 보고 있는가”를 먼저 확인할 수 있습니다.

프리팹에서 상속된 컴포넌트, 일반 C# 클래스, 수동 에디터 메뉴는 씬의 직접 참조 수가 0일 수 있습니다. **직접 참조가 0이라는 이유로 미사용 또는 삭제 가능이라고 판정하지 않습니다.** 삭제는 별도 참조 조사와 사용자 승인이 필요합니다.

이번 작성에서 파일 링크·코드 펜스·필수 장·스크립트 설명 포함 여부를 검사하고, 게임 코드·씬·에셋·기존 메타가 작성 전 해시와 같은지 비교합니다. 실제 결과는 함께 제공하는 [문서 검사 보고서](evidence/document_validation.json)에 기록합니다. 이 보고서는 문서의 링크와 보존 범위 검사이며 게임 전체의 무오류 보증이 아닙니다.

## SOLID 검토

SOLID는 파일 수를 무조건 늘리라는 규칙이 아닙니다. “누가 어떤 일을 맡고, 한 기능을 바꿨을 때 어디까지 영향이 가는가”를 판단하는 기준입니다.

| 원칙 | 현재 잘 나뉜 예 | 남은 결합·확인할 점 |
|---|---|---|
| S 단일 책임 | 설치 입력/시간/바닥/표시를 PlacementInput/Hold/Surface/Feedback으로 분리. PlayerController는 조립·실행 연결 중심 | ItemInteractor는 대상 발견·캐시·저장·포획 연결까지 포함. 추가 요구가 커질 때 분리 범위 재평가 |
| O 확장과 기존 동작 보존 | SetInputSource로 키보드 대신 AI/다른 장치 입력 연결. 획득 포트 교체 지점 존재 | TrapPlacement는 동일 trapItem과 ConsumableJawTrap 구체 타입 사용. 다른 종류 설치물은 추가 설계 필요 |
| L 대체 가능성 | 입력·조준·획득 공급자를 작은 계약으로 받음 | 인터페이스 구현 자체가 동작 대체 보증은 아님. 새 공급자도 차단·해제·busy·재호출 규칙을 지키는지 검사 필요 |
| I 작은 계약 | IPrimaryAction, IInteractionAction, IInteractionTargetQuery는 각기 입력 점유·대상 조회만 제공 | 거대한 플레이어 인터페이스로 합치면 카메라가 불필요한 인벤토리 기능까지 알아야 하므로 피함 |
| D 의존 방향 | 이동·점프·유지 시간 판단 일부가 Unity 타입을 쓰지 않음. 설정 적용은 IGameSettingsApplier 경계 사용 | 실제 생성·물리·UI와 GameManager/HotbarManager 단일 인스턴스 연결은 Unity에 의존. 완전한 엔진 독립을 주장할 수 없음 |

현재 코드리뷰는 위 경계를 확인한 것입니다. 새 코드 공급자의 동작을 실제로 바꾸어 LSP를 전부 증명한 시험은 아닙니다. 엔진을 바꾸면 순수 정책은 재사용할 여지가 있지만 Rigidbody, Input System, Cinemachine, Animator, UI, 물리 검사 어댑터는 다시 연결해야 합니다.

## 앞으로 수정할 때의 확인 절차

1. **대상 고르기:** F번호, 현재 파일, 실제 씬 인스턴스와 원본 프리팹 중 어느 쪽인지 확인합니다.
2. **현재 값 적기:** 고칠 값과 연결을 먼저 기록합니다. 기본값과 오버라이드를 구분합니다.
3. **작게 수정하기:** 하나의 책임을 바꾸고 관련 없는 이름·메타·GUID를 건드리지 않습니다.
4. **정적 확인:** 컴파일 오류, 끊긴 참조, 중복 GUID, 입력을 동시에 사용하는 담당자부터 확인합니다.
5. **실제 플레이 확인:** 메뉴/포커스/재입력/라운드 전환처럼 기능이 겹치는 상황을 검사합니다. 모델은 정면·측면·사선도 확인합니다.
6. **추적 자료 갱신:** 기능 장, 스크립트 색인, 작업 로그에 바뀐 이유·검사·남은 문제를 기록합니다. 새 시험 날짜를 남기고 오래된 PASS를 재사용하지 않습니다.
7. **협업 전 확인:** Git 변경 목록에서 요청 범위 밖 파일과 메타 재생성을 확인합니다. 커밋·푸시는 별도 승인 범위를 따릅니다.

문서만 고친 이번 작업에는 게임 빌드나 Play 실행이 필요하지 않습니다. 문서 링크·내용·보존 범위를 검사하는 것이 작업 유형에 맞는 검증입니다.
