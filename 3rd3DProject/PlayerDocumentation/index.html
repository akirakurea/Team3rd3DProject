3. F01 — 입력과 조작 권한

3.1 목적과 현재 규칙

메뉴를 조작하는 마우스 클릭이 물건 집기나 총 발사로 동시에 사용되지 않도록 합니다. ‘마우스가 보인다’와 ‘게임 조작이 가능하다’를 여러 스크립트가 제각각 결정하지 않게 공통 확인 경로를 둡니다.

GameplayInput.IsEnabled가 true이려면 다음 조건을 모두 만족해야 합니다.

  1. GameManager가 없거나 상태가 Playing 또는 RoundClear여야 합니다.
  2. 시간이 멈추지 않았어야 합니다. 기준은 Time.timeScale > 0입니다.
  3. 열린 메뉴 등에서 등록한 차단 요청이 없어야 합니다.
  4. Unity 게임 창이 포커스를 가지고 있어야 합니다.
  5. 커서가 Locked여야 합니다.
  6. 메뉴를 닫거나 잠금을 복구한 바로 그 프레임이 지나야 합니다.

따라서 결과 표시 전 RoundClear 구간은 공통 입력에서 허용합니다. 하지만 덫 설치처럼 더 좁은 상태 조건을 가진 기능은 따로 금지될 수 있습니다. 이 문서의 공통 허용과 모든 개별 기능의 허용을 같은 뜻으로 해석하지 않습니다. 근거: GameplayInput.cs 12~26행.

기본 이동 입력은 WASD이고 Shift는 달리기 요청, Space는 새로 눌렀을 때만 점프 요청입니다. InteractionInput은 좌클릭·숫자 1을 읽고, CombatInput은 좌클릭·우클릭을 읽습니다. 같은 버튼을 읽는다고 동시에 실행하는 것은 아닙니다. 장비·덫 선택·손 상태에 따른 실제 사용 결정은 각각의 상호작용/전투 연결부가 담당합니다.

  → 잠금 복구 프레임의 클릭/점프는 버림
  → 다음 정상 입력부터 게임 명령으로 사용

4. F02 — 이동, 작은 턱 넘기, 무마찰

4.1 목적과 현재 흐름

카메라를 돌린 뒤 W를 누르면 카메라가 보는 지면 방향으로 이동합니다. 걷기와 달리기 속도로 즉시 튀지 않고 현재 수평 속도에서 목표 속도로 가까워집니다. 낮은 턱은 넘을 수 있는 높이와 머리 위 공간을 확인한 뒤 조금씩 올라갑니다.

PlayerController.Update가 입력을 읽고 FixedUpdate가 실제 물리에 적용합니다. 화면 갱신과 물리 갱신의 횟수가 다를 수 있으므로 Space 누름은 pendingJump에 잠시 보관해 다음 물리 갱신에서 한 번만 사용합니다. 이 짧은 전달 보관과 뒤에서 설명할 ‘착지 전 0.15초 점프 버퍼’는 목적이 다른 두 단계입니다.

PlayerController.FixedUpdate
  → 이동 설정 묶음 만들기
  → PlayerJump.Step으로 점프 상태 확인
  → PlayerMovement.Apply
      → 카메라 전방을 지면에 눕혀 이동 방향 만들기
      → MovementPolicy로 걷기/달리기 속도 선택
      → 가속 제한 안에서 수평 속도 변경
      → 점프면 이륙 속도, 아니면 StepSolver의 턱 상승 결과 사용
      → Rigidbody.linearVelocity와 MoveRotation에 적용

4.2 코드 읽기

출처: Movement/PlayerMovement.cs 19~34행 중 이동 부분.

  • 둘째 줄은 방향에 걷기·달리기 속도를 곱해 목표 속도를 만듭니다.
  • 셋째 줄은 현재 물리 속도를 읽습니다.
  • 마지막 두 줄은 수평 속도만 목표에 가깝게 바꿉니다. 위아래 속도를 0으로 만들지 않기 때문에 중력·점프를 별도로 유지할 수 있습니다.

  • 이륙하는 딱 한 번에만 최초 상승 속도를 넣습니다. 계속 위로 떠오르는 힘을 매 프레임 넣지 않습니다.

  • 계산된 수평·수직 값을 한 곳에서 Rigidbody에 씁니다. 서로 다른 기능이 같은 속도를 덮어쓰는 일을 줄입니다.

4.3 작은 턱을 넘는 검사 순서

StepSolver.TryGetVerticalSpeed는 다음을 확인합니다.

  1. 턱 기능이 켜져 있고 입력과 수평 속도가 있는지 봅니다. 현재 지원 형태는 세로 CapsuleCollider(direction == 1)입니다.
  2. 캐릭터 발 아래에 실제로 설 수 있는 면이 있는지 확인합니다. 빠르게 상승·낙하 중이면 새 턱 넘기를 시작하지 않습니다.
  3. 발 앞에 낮은 장애물이 있는지 먼저 검사합니다. 없으면 더 비싼 공간 검사는 하지 않습니다.
  4. 장애물 뒤쪽 윗면을 내려다보며 높이와 경사를 확인합니다.
  5. 위로 올라갈 공간, 앞으로 갈 공간, 최종 도착 위치의 몸 공간을 검사합니다.
  6. 통과하면 목표 발 높이를 저장하고 최대 상승 속도 안에서 조금씩 올립니다.
  7. 방향을 크게 바꾸거나 제한 시간이 지나거나 머리 위가 막히면 상승을 중단합니다.

높이만 낮다고 무조건 벽을 통과시키는 방식이 아닙니다. 턱 위의 공간까지 확인합니다. 검사 배열은 24개씩 재사용합니다. 결과가 배열을 가득 채울 만큼 복잡한 곳에서는 누락 위험 때문에 검사를 실패로 처리합니다. 이는 안전한 거부 방식이지만, 충돌체가 매우 많은 지점에서는 넘을 수 있어 보이는 턱도 거절될 수 있다는 한계가 있습니다. 근거: StepSolver.cs 35106, 131162행.

4.4 마찰은 스크립트의 가짜 물리가 아님

Player_NoFriction.physicMaterial에는 정지 마찰 0, 움직이는 중의 마찰 0이 저장되어 있습니다. InteractionSettings.cs 19~31행은 기존 물리 재질이 Multiply 조합인지 확인하고 플레이어 Rigidbody에 속한 비 Trigger 충돌체에 연결합니다. Rigidbody의 linearDamping도 0으로 연결합니다.

마찰 0과 이동 감속은 다릅니다. 바닥이 붙잡는 힘은 줄여도, PlayerMovement는 키를 떼면 목표 수평 속도 0으로 가까워지도록 계산합니다. 따라서 무마찰이라고 얼음 위처럼 끝없이 미끄러져야 하는 것은 아닙니다. 상대 충돌체의 재질 조합 방식도 최종 접촉 마찰에 영향을 줄 수 있으므로, 실제 씬에서는 양쪽 재질을 같이 확인해야 합니다.

좋은 점: 지형 검사는 IStepSolver, 실제 물리 쓰기는 PlayerMovement, 실행 순서는 PlayerController로 나뉩니다(SRP). 다른 턱 검사기를 연결할 수 있어 구현 교체 지점도 분명합니다(DIP/OCP). 다만 IStepSolver의 계약 자체는 Vector3를 사용하므로 엔진 독립 인터페이스가 아닙니다. MovementPolicy는 엔진을 바꾸어도 옮기기 쉽지만 물리·좌표 연결부는 교체해야 합니다.

initialized = true;
wasMoving = false;
float halfAngle = Math.Max(0f, Math.Min(180f, stationaryHalfAngle));
float offset = Normalize(currentYaw - stationaryCenter);
float value = stationaryCenter + Math.Max(-halfAngle, Math.Min(halfAngle, offset));
  • 아직 기준이 없거나 방금까지 이동했다면 현재 카메라 방향을 새 기준으로 저장합니다.
  • 이후 정지 중에는 기준을 계속 따라 움직이지 않도록 wasMoving을 false로 바꿉니다.
  • 설정 범위를 0~180도로 제한합니다.
  • 지금 각도와 기준의 차이를 -180~180도 범위로 정리합니다.
  • 허용 범위 밖의 각도는 끝값에 붙입니다. 캐릭터가 멈출 때 보고 있던 방향이 중심입니다.

CameraOrbitLimit.Update는 실행 순서 100으로 일반 입력 Update 뒤에 적용합니다. 기본 자동 중앙복귀(Recentering)는 이 제한을 적용하는 동안 끕니다. 컴포넌트를 끄면 시작 때 저장한 범위·중심·반복 회전·중앙복귀 설정을 되돌립니다. 이것은 에셋 파일을 복원하는 것이 아니라 실행 중 변경한 Cinemachine 축 설정을 정리하는 동작입니다.

5.3 ESC 설정창에서 마우스가 사라지던 문제를 피하는 현재 구조

CameraCursorLock은 메뉴가 열려 있을 때의 잠금 요청을 거절합니다. 메뉴를 닫고 조작 권한이 다시 허용되면 잠금을 바로 같은 프레임에 쓰지 않고 예약합니다. ESC가 해제되고 요청 프레임 다음이 된 뒤에 잠급니다. Unity Editor도 ESC로 커서를 해제할 수 있기 때문에 같은 프레임에서 잠금·해제가 싸우지 않게 한 것입니다.

출처: CameraCursorLock.cs 45~49행.

if (capturePending)
{
    if (!GameplayInput.CanCaptureCursor) capturePending = false;
    else if (Time.frameCount > captureRequestedFrame &&
             (keyboard == null || !keyboard.escapeKey.isPressed))
        SetLocked(true);
}
  • 잠금을 예약해 두었을 때만 이 경로를 사용합니다.
  • 그 사이 다시 메뉴가 열리거나 창 포커스를 잃으면 예약을 취소합니다.
  • ESC를 아직 누르고 있거나 예약한 그 프레임이면 기다립니다.
  • 조건이 맞을 때만 잠급니다. SetLocked 내부에서도 권한을 한 번 더 확인합니다.

이 코드만으로 UI 클릭 전체가 작동하는 것은 아닙니다. UI에는 정상 EventSystem과 UI 입력 모듈, Raycast 대상, 버튼 연결도 있어야 합니다. 커서가 보이는데도 버튼이 작동하지 않으면 그 연결을 별도로 확인해야 합니다. 반대로 메뉴 표시 코드는 실제 Cursor 값을 직접 쓰지 않고 GameplayInput.SetBlocked로 권한만 요청하는 것이 현재 역할 분리입니다.

5.4 우클릭 조준 확대

AimZoom.aimSource는 IAimState.IsAiming만 읽습니다. 켜질 때 기존 Cinemachine 시야각을 기억하고, 조준하면 설정 시야각으로 좁히며, 해제하면 원래 값으로 돌아갑니다. 기본 조준 시야각은 40도, 전환 시간은 0.16초입니다. 기본 시야각이 이미 40도보다 좁다면 줌 때문에 더 넓어지지 않습니다.

출처: AimZoom.cs 37~42행.

float target = aiming
    ? Mathf.Min(originalFieldOfView, Mathf.Clamp(aimedFieldOfView, 1f, 179f))
    : originalFieldOfView;
float next = transitionSeconds <= 0f ? target : Mathf.SmoothDamp(
    virtualCamera.Lens.FieldOfView, target, ref zoomVelocity,
    transitionSeconds, Mathf.Infinity, Time.unscaledDeltaTime);
virtualCamera.Lens.FieldOfView = next;
  • 조준 중이면 원래보다 같거나 좁은 시야각을 고릅니다.
  • 조준하지 않으면 처음 기억한 시야각을 고릅니다.
  • 전환 시간이 0이면 즉시 바꾸고, 아니면 조금씩 부드럽게 따라갑니다.
  • unscaledDeltaTime은 게임 시간 배율에 영향을 받지 않는 시간입니다. 메뉴 등으로 게임 시간이 멈출 때의 시각적 복귀와 관련됩니다.
  • Main Camera에 직접 쓰지 않고 Cinemachine 렌즈에 결과를 씁니다.

5.5 수정법·검사·설계 리뷰

Inspector에서 구도는 Cinemachine의 Follow/Orbit 설정, 수평 제한은 CameraOrbitLimit.stationaryHalfAngle, 확대는 AimZoom.aimedFieldOfView와 transitionSeconds를 수정합니다. 포인터 위치를 움직여 카메라 구도 문제를 숨기지 않습니다. 현재 공통 설정 적용 분리 기록에서는 마우스 감도 UI 값을 카메라에 새로 연결하는 일은 별도 범위였습니다. 해당 슬라이더가 존재한다는 이유만으로 감도 연결까지 완료되었다고 단정하지 않습니다.

검사는 다음처럼 구분합니다.

  • 이동 중 수평으로 한 바퀴 회전한 뒤 멈춰 좌우 끝을 확인합니다.
  • 다른 방향을 본 상태에서 다시 이동→정지하여 새 기준이 정지 순간으로 바뀌는지 봅니다.
  • 위아래 회전은 기존 수직 범위를 유지하는지 봅니다.
  • ESC 열기→버튼 클릭/드래그→ESC 닫기 후 잠금 복구를 확인합니다.
  • Alt+Tab으로 포커스를 잃었을 때 잠금이 강제로 되살아나지 않는지 봅니다.
  • 조준 줌·해제·장비 해제를 반복하고 Main Camera의 실제 화면이 자연스럽게 복귀하는지 봅니다.

좋은 점: OrbitPolicy에는 Unity 코드가 없고, 카메라는 전체 플레이어 구현이 아니라 IMotionState·IAimState라는 작은 계약을 읽습니다(DIP/ISP). 커서 쓰기도 한 컴포넌트로 모았습니다(SRP). 현재 제한: motionSource·aimSource는 Inspector 연결을 위해 MonoBehaviour로 저장한 뒤 실행 중 인터페이스를 확인합니다. 잘못된 종류의 컴포넌트를 넣으면 자동으로 올바른 대상을 찾아 주지 않습니다. 연결 검사가 필요합니다. Cinemachine 전용 축·렌즈 코드는 다른 엔진에서 그대로 사용할 수 없습니다.

6. F04 — Animator, 점프 모션, 사격 자세와의 연결

6.1 실제 이동과 모양 변형의 분리

이동·점프에는 두 가지 변화가 있습니다.

  1. 캐릭터 전체가 바닥 위에서 이동하고 실제로 떠오르는 변화: Rigidbody가 담당합니다.
  2. 몸이 눌리고 늘어나며 손·귀·꼬리의 자세가 바뀌는 변화: Animator가 클립의 본 곡선을 읽고, 스키닝된 메시가 본을 따라 변형됩니다.

PlayerAnimation 생성자는 animator.applyRootMotion = false로 설정합니다. 모션의 루트 이동을 다시 캐릭터 위치에 더해 물리 이동과 중복시키지 않기 위한 구성입니다. 사격할 때 총과 양손은 Animator 평가 뒤 장비 자세 보정을 추가로 받을 수 있습니다. ‘본만 움직이고 메시 외형은 고정’인 구조가 아닙니다. 본의 변형이 스키닝된 메시의 모양을 바꿉니다. 다만 이 문서의 C# 검토만으로 모든 메시의 스킨 가중치 품질을 재검증했다고 주장하지 않습니다.

6.2 이동·점프 상태 그래프

현재 읽은 PlayerJump.controller는 Base Layer에 Idle·Walk·Run·Jump가 있고 Shotgun 레이어에 Ready·Fire가 있습니다.

매개변수 타입 값의 의미 값을 보내는 코드
Movement Int 0 대기 / 1 걷기 / 2 달리기 PlayerAnimation.Apply
JumpActive Bool 점프의 준비·공중·착지 단계 진행 중 PlayerAnimation.Apply
JumpTime Float 정책의 2초 기준 자세 시간을 0~1로 바꿔 클립 위치 지정 PlayerAnimation.Apply
ShotActive Bool 발사 클립 진행 여부 ShotgunPose.Tick
ShotTime Float 발사 클립의 현재 자세 위치 0~1 ShotgunPose.Tick

점프 진입은 Any State → Jump 공통 화살표 하나입니다. 이것이 Idle·Walk·Run에서 모두 점프로 들어가는 경로입니다. 각 상태에서 Jump로 따로 선이 세 개 보이지 않는다고 역방향 연결이 없는 것은 아닙니다. Jump가 끝나면 Movement에 따라 대기·걷기·달리기로 돌아갑니다. 현재 컨트롤러 파일의 고정 전환 시간은 점프 진입 0.08초, 점프 복귀 0.15초, 지상 이동 상태 사이 0.12초입니다. 근거: Controller 23, 48, 105, 161, 189, 272, 390, 505, 558, 586행.

출처: PlayerAnimation.cs 58~64행.

animator.SetInteger(Movement, (int)MovementPolicy.SelectAnimation(intent));
animator.SetBool(JumpActive, jumpFrame.Active && SupportsJump);
if (SupportsJump && jumpFrame.Active)
    animator.SetFloat(jumpTime, Mathf.Clamp01(jumpFrame.PoseTime / 2f));
  • 현재 입력 의도를 숫자 0·1·2로 바꿔 Animator에 줍니다.
  • 점프 연결이 준비되어 있고 점프가 진행 중일 때만 JumpActive를 켭니다.
  • 정책의 자세 위치를 기준값 2로 나눠 0~1로 바꿉니다. 실제 Jump.anim의 저장된 m_StopTime은 1.2초이므로, 이 2를 실제 클립 길이라고 설명하면 안 됩니다. 정규화된 비율로 현재 클립의 자세를 선택합니다.
  • 점프 종료 직후에는 JumpTime을 0으로 다시 쓰지 않습니다. 복귀 혼합 동안 나가는 Jump 자세도 아직 사용되므로, 0으로 되돌리면 마지막 착지 자세가 갑자기 점프 준비 자세로 되감길 수 있기 때문입니다.

SupportsJump는 이름만 보고 true가 되지 않습니다. Movement(Int)·JumpActive(Bool)·JumpTime(Float) 매개변수와 Base Layer의 Jump 상태가 있어야 합니다. 설정 jumpSettings.enabled도 켜져야 물리 점프가 활성화됩니다.

6.3 점프 단계와 버퍼

단계 쉬운 설명 다음 단계 조건
Ready 일반 대기·걷기·달리기 바닥 위에서 새 Space 또는 유효한 보관 입력
Anticipation 뛰기 전에 몸을 누르는 준비 일반 준비 0.40초가 지나면 한 번 이륙
Airborne 실제로 떠오르고 내려오는 중 바닥 지지, 수직 속도, 최소 공중 시간 조건 만족
Landing 착지 충격과 회복 이동 중에는 짧은 회복, 정지 중에는 나머지 착지 자세

코드의 TakeoffTime=.40, ApexTime=.855, TouchdownTime=1.31, ClipEnd=2는 정책의 가상 시간표입니다. PlayerAnimation은 이 값을 2로 나눈 비율을 현재 1.2초 클립에 전달합니다. 공중을 무조건 2초 동안 날게 만드는 상수가 아닙니다. 공중 자세는 실제 수직 속도로 고르며, 높이·중력에 따라 실제 체공 시간이 달라집니다. 오래 떨어지는 동안은 착지 직전 자세 범위에 머뭅니다. 일반 절벽 낙하를 별도의 새 낙하 상태로 처리하는 기능은 이 정책에 추가되어 있지 않습니다.

PlayerJump가 계산하는 최초 상승 속도는 다음과 같습니다. 출처: PlayerJump.cs 50~53행.

LaunchSpeed = Mathf.Sqrt(2f * Mathf.Max(0.05f, settings.height) * -Physics.gravity.y);
IsGrounded = HasSupport() && body.linearVelocity.y <= 0.2f;
return policy.Step(pressed, IsGrounded, body.linearVelocity.y, deltaTime, LaunchSpeed,
    Mathf.Max(0f, settings.jumpBufferSeconds), inputEnabled, moving);
  • 원하는 높이와 Unity 중력으로 출발 속도를 구합니다. 이후의 중력은 Unity가 처리합니다.
  • 발 아래 지지면이 있어도 아직 빠르게 올라가는 중이면 착지로 인정하지 않습니다.
  • ‘키를 눌렀는지, 바닥인지, 수직 속도는 얼마인지’라는 관측값을 정책에 전달합니다.
  • 정책은 올라갈지·착지할지 판단할 뿐 이 함수에서 Rigidbody 속도를 직접 쓰지는 않습니다.

기본 jumpBufferSeconds는 0.15초입니다. 착지 직전에 Space를 너무 일찍 눌러도 그 요청을 잠깐 기억하고 바닥에 닿았을 때 사용할 수 있습니다. 길게 누르는 자동 연속 점프나 공중 추가 점프를 뜻하지 않습니다. 버퍼가 만료되면 요청은 사라집니다. 메뉴·포커스 차단·입력 공급자 변경 시 아직 사용하지 않은 요청은 취소합니다.

착지 직후 0.13초 안의 압축 자세에서 다음 점프가 예약되면, 준비 시간을 이미 진행한 것으로 보고 착지 자세를 거꾸로 이어 이륙합니다. 이동 중 착지 회복은 기본 정책상 0.18초 뒤 지상 모션으로 일찍 돌아갈 수 있습니다. 이미 몸이 많이 펴진 뒤 새 점프를 누른 경우까지 무조건 압축 자세로 되돌리지는 않습니다. 이 세부 분기는 JumpPolicy.Step 113139행, BeginAnticipation 179186행, PreparationPoseTime 189~196행에 있습니다.

6.4 사격 후 모션 정지를 막는 현재 연결

ShotgunPose는 본 애니메이션 전체를 멈추는 대신 Shotgun 레이어의 ShotActive·ShotTime만 제어합니다. 현재 Controller의 Ready와 Fire는 모두 발사 클립을 연결하고 Write Defaults가 false입니다. Ready의 Speed는 0이며 Fire는 ShotTime 매개변수로 클립 위치를 제어합니다. 읽은 발사 클립의 바인딩은 raiseWeight·recoilDistance·recoilPitch라는 ShotgunPose의 숫자 세 종류입니다. 현재 파일에서 확인한 구성은 Controller 204218, 433452행 및 발사 클립 6366, 120123, 177~180행에 있습니다.

‘Ready가 비어 있어도 된다’며 임의로 Motion을 제거하거나, 사격 레이어에서 모든 본의 기본값을 강제로 덮어쓰는 설정을 추가하면 지상 모션과의 관계를 다시 검증해야 합니다. 이전 오류 수정 경위는 작업 로그를 근거로 추적하고, 여기서는 현재 파일 구성을 확인한 사실과 분리합니다.

발사 준비·판정·반동의 순서는 다음과 같습니다.

전투 코드가 BeginShot 호출
  → Tick이 준비 시간을 진행
  → 준비 시각 fireMoment에 도달하면 ReadyToFire
  → 장비의 최신 총구 자세가 적용된 뒤 실제 발사 판정
  → AcknowledgeShot
  → 반동 구간 진행
  → 클립 끝에서 ShotActive 해제

판정 전에 반동만 먼저 진행되지 않도록 SampleTime은 판정 승인 전 fireMoment에서 멈춥니다(ShotgunPose.cs 68~69행). 기본 fireMoment와 raiseSeconds는 각각 0.12초이며 실제 씬 값과 클립 길이를 함께 맞춰야 합니다.

총은 조준점 쪽으로 향하도록 ShotgunPose.Apply가 보정하고, 양손은 ShotgunEquipment.LateUpdate에서 그립 위치를 따라갑니다. 다음 Update에서 이전 손 보정을 되돌린 뒤 Animator가 새 모션을 계산하므로 이전 프레임의 손 위치 보정이 계속 쌓이는 것을 피합니다. 총구가 너무 가까운 목표 때문에 뒤집히지 않게 앞쪽 보조 목표를 쓰는 분기도 있습니다. 이 자세 보정은 실제 총구 벽 판정을 대신하지 않습니다.

6.5 남아 있는 구형 컨트롤러 호환 경로

현재 코드에서 CrossFadeInFixedTime과 AnimationClip.SampleAnimation이 보인다고 모두 미사용 중복은 아닙니다.

  • PlayerAnimation.ApplyLegacyController는 Movement·JumpActive 매개변수가 없는 구형 Idle.controller를 위한 대기·걷기·달리기 호환 경로입니다.
  • ShotgunPose.Tick의 SampleAnimation 경로는 Shotgun 레이어·매개변수가 없는 컨트롤러에서만 사용됩니다.
  • 새로운 PlayerJump.controller 경로에서는 Animator 상태 그래프와 매개변수를 사용합니다.

1. 처음 읽는 사람을 위한 개념

4. F05 — 좌클릭 물건 운반

4.1 목적과 데이터 흐름

목적은 빈손으로 집을 수 있는 물체를 중앙 포인터에 가까이 들고, 버튼을 떼면 자연스럽게 놓는 것입니다. 인벤토리에 저장하는 기능과 다릅니다.

마우스 좌클릭 → InteractionInput → HandInput
→ InteractionController가 현재 손 상태 구성
→ HandPolicy가 Pickup/Release 결정
→ ItemCarrier가 물리 상태 변경 및 위치 이동
→ 놓을 때 Collider 복구 + Rigidbody 중력 재개

현재 손에 총이 있거나, 이미 물건을 들었거나, UI 획득 연출 중이면 HasFreeHands가 false입니다. 조준 대상은 카메라 중앙에서 가장 가까운 물체를 찾은 다음 플레이어 몸통의 기준점에서 다시 벽에 가려지는지 확인합니다. 카메라가 벽 너머 물체를 보더라도 플레이어 손이 벽을 뚫고 집지 않도록 두 번 검사하는 것입니다.

근거: InteractionController.cs 3643행, 134150행.

4.2 핵심 코드 읽기: 언제 집을 수 있는가

  2. 둘째 줄은 총을 든 채 숫자 1을 누르면 총을 해제하라는 뜻입니다.

이 함수는 Unity 오브젝트를 움직이지 않습니다. 명령만 고르므로 작은 단위 검사를 하기 쉽고 다른 입력 장치에서도 재사용할 수 있습니다.

4.3 집은 물건이 이동하는 과정

ItemCarrier.TryGrab은 먼저 기존 속도, 충돌 상태 및 표시 크기를 확인합니다. 보유 중에는 isKinematic=true, useGravity=false로 바꾸고 물건의 Collider들을 일시 비활성화합니다. 그래서 물리 엔진이 손의 이동과 서로 경쟁하지 않습니다. 대신 이 운반 코드는 BoxCastNonAlloc과 OverlapBoxNonAlloc으로 길과 도착 공간을 직접 검사합니다.

선반의 턱에 걸리지 않게 이동은 세 단계입니다.

  1. 현재 위치에서 0.08만큼 위로 들어 올립니다.
  2. 들어 올린 높이를 유지하며 선반에서 수평으로 꺼냅니다.
  3. 중앙 조준선의 보유 지점을 따라갑니다.

중앙점의 위치는 화면 좌표를 임의로 옮기는 방식이 아닙니다. 카메라 중앙의 선 위에서 플레이어 깊이와 보유 거리를 더한 지점을 구합니다. 기본 holdDistance는 0.8입니다. 장애물이 있으면 포인터 위치보다 물리 충돌을 우선하여 물건이 더 멀리 가지 못합니다.

근거: ItemCarrier.cs 4679행, 93109행, 122127행, 162188행.

4.5 Inspector 설정과 외형 교체

운반 대상에는 CatInteractionItem이 필요하고, 이 컴포넌트는 루트의 BoxCollider와 Rigidbody를 요구합니다. Kind를 CarryOnly로 설정하고 Visual Root에 실제 모델이 들어 있는 자식을 지정합니다. Visual Root로 자기 자신이나 다른 계층의 모델을 연결하면 RefreshVisual이 유효한 외형으로 취급하지 않습니다.

외형을 교체할 때는 루트의 식별자와 물리 컴포넌트를 유지하고 Visual 아래의 모델을 교체합니다. 그 다음 컴포넌트 메뉴의 Visual 크기에 맞춰 충돌 갱신을 실행합니다. 이 함수가 렌더러들의 경계 크기를 루트 좌표로 바꿔 BoxCollider의 중심과 크기를 계산합니다. 손에 들고 있는 동안 바꾸지 말고 내려놓은 상태에서 갱신하세요.

InteractionController의 Reach는 선택 거리, Hold Distance는 든 위치입니다. 둘은 목적이 다르므로 “더 멀리 있는 물건을 집고 싶다”면 Reach를, “들었을 때 얼굴과 겹친다”면 Hold Distance를 조정합니다. Solid Layers는 벽을 포함한 충돌 검사 범위이므로 특정 아이템 레이어만 넣으면 벽 가림 검사가 약해질 수 있습니다.

4.6 수정 후 확인할 일

  • 빈손에서 좌클릭 유지/해제가 각각 한 번의 집기/놓기로 이어지는지 확인합니다.
  • 선반에서 꺼낼 때 위→수평→보유 순서가 자연스러운지 확인합니다.
  • 벽에 가까이 다가가도 물건이 벽을 통과하지 않는지 확인합니다.
  • 들고 있던 중 ESC 또는 창 포커스 상실 시 물건이 공중에 고정되지 않는지 확인합니다.
  • 놓은 물체가 현재 위치에서 떨어지는지, 예전 위치나 바닥으로 순간 이동하지 않는지 확인합니다.

5. F06 — F 아이템 저장과 Enemy 포획

5.1 현재 코드는 레이어 이름만으로 등록하지 않습니다

현재 ItemInteractor.cs에는 Item/Enemy 이름을 읽는 LayerMask, NameToLayer, itemLayers, enemyLayers 판정 코드가 없습니다. 과거 요청이나 작업 설명에 레이어 사용이 적혀 있더라도, 현재 읽은 소스만 기준으로는 레이어를 붙이기만 하면 F 대상이 되는 구조가 아닙니다.

현재 대상 발견 경로는 다음 세 가지입니다.

  1. Targets 목록이나 실행 중 Register로 명시적으로 등록한 대상.
  2. 충돌체에서 부모 방향으로 찾은 ItemPickup에 유효한 아이템 데이터가 있고, CanPickup=true인 대상. Use Item Pickup Registration이 켜져 있어야 합니다.
  3. 충돌체 또는 그 부모에 ThiefController가 있는 대상. 발견하면 Enemy 종류로 등록합니다.

코드는 충돌체에서 위쪽으로만 올라갑니다. 부모에 큰 Collider가 있고 아래 자식에만 ItemPickup이 있으면 자동 발견 경로가 그 자식으로 내려가지는 않습니다. 또한 useItemPickupRegistration이 꺼졌을 때 Enemy의 비트리거 선택과 트리거 허용 코드 조건이 서로 다릅니다. 비트리거는 ThiefController를 찾지만 트리거 허용은 해당 옵션을 확인합니다. 이 차이는 Inspector 옵션을 바꿀 때 검사해야 할 현재 구조의 경계입니다.

근거: ItemInteractor.cs 118138행, 162201행. 일반 Raycast가 어떤 레이어를 통과하는지는 InteractionController.solidLayers에서 별도로 제한됩니다.

5.2 일반 아이템의 저장 흐름

F 새 누름 → 입력 권한 및 설치의 F 점유 확인
→ 중앙 조준선/거리/벽 검사
→ 등록 대상 또는 ItemPickup 데이터 발견

기존 HotbarManager는 HotbarStore라는 작은 연결부를 통해 IItemInventory 계약으로 사용합니다. ItemInteractor가 필요한 기능은 빈칸 조회와 추가 요청뿐입니다. UI 선택 강조, 마우스 휠, 전체 슬롯 그림을 직접 관리하지 않습니다. 다른 저장소를 연결하려면 TrySetInventory를 사용하되 획득을 처리하는 중에는 교체가 거부됩니다.

F 경로 수정 뒤에는 빈손/물건 보유/총 장착의 세 상태에서 각각 일반 아이템과 기절한 Enemy를 검사해야 합니다. 인벤토리 빈칸이 없는 경우에는 아이템이 사라지지 않는지, Enemy 포획에는 저장소 빈칸이 필요하지 않은지 함께 확인합니다.

6. F07 — 중앙 커서, 노란 강조, UI 획득 연출

6.1 중앙 구체와 산탄 원의 차이

CenterCursor의 기본 지름은 6픽셀입니다. 카메라 바로 앞에 구체를 놓고, 시야각과 화면 높이로 실제 크기를 역산합니다. 그래서 화면 해상도나 카메라 거리와 관계없이 화면 가운데의 작은 표시로 보이게 합니다. 커서 잠금이 풀리면 구체도 숨깁니다.

CatCursorSphere.shader는 반투명 흰색과 얇은 테두리를 그립니다. 실제 벽의 깊이에 가려지지 않도록 표시용 셰이더로 동작합니다. 이 구체 자체에 아이템 선택 Collider를 붙이는 방식이 아닙니다. 산탄 원은 이와 별도의 ShotSpreadRing입니다.

6.2 노란 강조는 원본 재질을 바꾸지 않습니다

ItemHighlight는 IHighlightSource가 제공한 Renderer와 메시를 사용해 면, 후광, 테두리를 추가로 그립니다. InteractionController가 만든 이 보조 객체가 담당하며, 모든 물체에 같은 무거운 상호작용 컴포넌트를 붙여야 하는 구조는 아닙니다.

일반 모델에는 HighlightTarget만 붙여도 강조 대상으로 사용할 수 있습니다. 단, 조준용 활성 Collider가 필요합니다. 이 컴포넌트는 강조 권한만 주므로 물건 집기나 F 저장까지 자동 허용하지 않습니다. 들 수 있는 물건은 CatInteractionItem, F 데이터 아이템은 ItemPickup이나 등록 목록을 별도로 갖춰야 합니다.

렌더링 과정은 다음과 같습니다.

  1. 대상을 바꾸면 그 모델의 메시 목록을 준비합니다.
  2. 일반 메시의 읽기가 허용되면 같은 위치 정점의 법선을 모아 테두리가 갈라지는 현상을 줄입니다.
  3. 움직이는 스킨 메시라면 BakeMesh로 현재 본 자세를 메시 모양에 반영합니다.
  4. Draw에서 면, 후광, 테두리를 그립니다.
  5. 최근 대상 하나는 캐시해서 조준이 잠깐 벗어났다 돌아와도 매번 다시 만들지 않습니다.
  6. 모델 교체/비활성화/폐기 때 직접 만든 임시 메시를 정리합니다.

근거: ItemHighlight.cs 2581행, 84132행. 강조 셰이더 CatInteractionOverlay.shader의 _Color, _Extrusion, _Cull로 색과 바깥 확장량을 정합니다. _Extrusion은 월드 공간 두께이므로 화면 픽셀 고정 두께와 다릅니다.

스킨 강조의 크기는 특별히 검사해야 합니다. 현재 45·109행은 BakeMesh(..., true)를 사용하고 120행은 localToWorldMatrix로 그립니다. 베이크 시 스케일을 포함시키는 설정과 그릴 때의 변환 행렬이 함께 적용되므로, 모델/부모 스케일이 1이 아닌 경우의 실제 결과를 비교해야 합니다. 이는 현재 코드에서 발견한 검증 지점이며, 이 문서 작업만으로 특정 RAt 크기 문제를 재현·수정했다고 주장하지 않습니다.

6.3 UI 획득 연출은 저장소가 아닙니다

InventoryPickupEffect는 등록된 inventoryTarget이 존재하고 활성 Canvas 위에 보일 때만 시작합니다. 연결이 없으면 임의의 화면 모서리로 보내지 않고 실패합니다. RegisterTarget(null)로 해제하거나 연출 중 UI가 사라지면 예약된 월드 물체 상태를 복구합니다.

기본 연출 값은 시간 0.55초, 화면 위로 휘는 높이 100, 마지막 크기 0.12배, 촬영 해상도 256입니다. 실제 Inspector 저장값은 별도입니다. 연출은 Time.unscaledDeltaTime을 쓰므로 timeScale=0만으로 자동 정지되지 않습니다. UI를 닫거나 연출 담당을 비활성화하면 취소 경로가 실행됩니다.

핵심 순서는 다음과 같습니다.

UI 목적지 유효성 확인
→ 실제 외형을 임시 카메라로 한 번 촬영
→ PickupReservation이 월드 표시·충돌·물리 상태를 저장하고 숨김
→ 아이콘이 UI로 이동
→ 도착하면 예약 완료 + Collected(itemId)
→ 취소하면 원래 표시·충돌·물리 상태 복구

InventoryPickupEffect.cs 188~197행 중 발췌:

PickupReservation completed = reservation;
reservation = null;
activeTarget = null;
bool committed = completed != null && completed.TryCommit(out itemId);
ClearPresentation();
if (committed) collected?.Invoke(itemId);
  1. 끝낼 예약을 임시 변수로 보관합니다.
  2. 현재 예약부터 비웁니다. 완료 이벤트 안에서 다시 호출해도 같은 물체를 두 번 완료하지 않기 위함입니다.
  3. 현재 목적지 연결도 비웁니다.
  4. 물체가 아직 유효한 경우에만 예약을 완료합니다.
  5. 아이콘과 촬영 텍스처를 정리합니다.
  6. 성공했을 때만 아이템 ID를 알립니다.

이 발췌는 읽기 쉽게 중간의 string itemId = null; 선언을 생략한 것입니다. 그대로 복사하여 독립 함수로 실행할 코드가 아니라 원래 함수의 핵심 순서를 설명한 코드입니다.

완료 알림은 저장 성공을 보장하지 않습니다. Collected 수신자가 연결되지 않았으면 아이콘 연출은 끝나도 Hotbar에 저장되지 않을 수 있습니다. F 획득은 별도의 직접 저장 경로이므로 F로 넣는 모든 아이템에 이 비행 연출이 자동 붙는다고 설명하면 안 됩니다.

6.4 촬영용 객체와 리소스의 정리

ItemIconCapture는 임시 카메라와 Light, 표시용 메시를 월드의 먼 위치에 만들고 전용 레이어 31만 찍습니다. 원본 Renderer나 공유 Material은 바꾸지 않고 필요한 PropertyBlock 값을 복사합니다. URP에서는 지원되는 RenderPipeline.StandardRequest로 촬영합니다. 지원하지 않거나 실패하면 false를 반환합니다.

성공/실패 여부와 관계없이 finally에서 임시 루트를 먼저 비활성화하고 생성한 메시를 파괴합니다. 촬영한 RenderTexture는 연출이 끝날 때 Release합니다. “한번 생성한 아이콘을 영구 에셋으로 저장”하는 기능은 아닙니다.

6.5 수정 후 확인할 일

  • 화면 비율을 바꿔도 중앙 구체가 가운데에 있고 크기가 과도하게 커지지 않는지 확인합니다.
  • 일반 메시와 움직이는 스킨 메시를 각각 강조하고, 오브젝트 스케일을 작게/크게 한 경우도 비교합니다.
  • 원본 Material 색이 바뀌지 않는지, 조준을 벗어나면 추가 강조만 없어지는지 확인합니다.
  • UI 목적지 미등록/비활성 상태에서 물체가 사라지지 않는지 확인합니다.
  • 정상 도착에서 이벤트가 1회인지, 연출 도중 UI 제거 시 이벤트 없이 물체가 복구되는지 확인합니다.
  • 여러 번 획득한 뒤 임시 CatItemIconPreview나 RenderTexture가 계속 쌓이지 않는지 확인합니다.

7. F08 — 샷건 장착·조준·발사

7.1 장착과 손 자세

숫자 1의 의미는 기존 총을 보이게 하거나 숨기는 토글입니다. 소환 연출을 재생하는 방식이 아닙니다. ShotgunEquipment는 씬에 준비된 weaponRoot와 몸통 본 motionRoot를 연결받습니다. 총 루트는 손 본 아래가 아니라 플레이어 아래에 두고, 손의 변형 본을 총의 leftGrip과 rightGrip 위치로 맞춥니다.

매 프레임 이전 손 보정을 먼저 복구하고, Animator가 기본 자세를 계산한 뒤 LateUpdate에서 총 위치와 양손 잡는 위치를 다시 적용합니다. 이 순서가 필요한 이유는 손 위치를 계속 더하기만 하면 조금씩 틀어지기 때문입니다.

근거: ShotgunEquipment.cs 7579행, 104117행. 잘못 연결된 루트가 Player 자신이나 부모인 경우 모델을 끄다 Player 전체가 꺼지지 않도록 HasValidBindings 및 SetWeaponVisible에 방어 조건이 있습니다.

7.2 조준과 걷기 고정

장착이 준비된 상태에서 우클릭을 유지하면 ShotgunCombat.IsAiming=true가 됩니다. AimZoom은 이 값만 읽고 Cinemachine 렌즈의 시야각을 줄입니다. 기본 목표 시야각은 40도, 전환 시간은 0.16초입니다. Main Camera의 Transform을 사격 코드가 직접 움직이는 방식이 아닙니다.

CombatPolicy.RestrictMovement는 조준 중 이동 의도에서 달리기 플래그만 제거합니다. 따라서 우클릭 중 Shift를 눌러도 걷고, 이동키를 누르지 않으면 대기합니다. 조준했다고 자동으로 걷기 애니메이션을 재생하는 것은 아닙니다.

IAimState는 조준 여부와 카메라 방향으로 몸을 돌릴 필요만 알립니다. 이동과 카메라가 샷건 내부의 발사 횟수나 총구 계산을 알아야 할 필요가 줄어듭니다.

7.5 카메라 조준선과 총구 광선은 다릅니다

카메라에서 쏜 선은 어디를 겨냥할지 고릅니다. 실제 산탄은 총구 앞쪽 +Z에서 출발합니다. 이 두 위치가 다르기 때문에 총구가 벽 안에 있는데 카메라만 벽 너머를 보는 경우를 따로 검사해야 합니다.

HitscanQuery.Cast는 다음 순서로 검사합니다.

  1. 몸통 기준점이 벽 안에 겹쳤는지 확인합니다.
  2. 몸통에서 총구까지 굵기가 있는 선을 쏘아 중간 벽을 찾습니다.
  3. 총구 자체가 벽 안에 겹쳤는지 확인합니다.
  4. 문제가 없으면 총구의 실제 앞 방향에 산탄 각도를 더해 광선을 쏩니다.
  5. 플레이어 자신과 자식 충돌체는 제외하고 가장 가까운 외부 충돌체를 고릅니다.

결과는 Miss(빗나감), Hit(명중), Blocked(총구 쪽이 막힘), QueryOverflow(검사 배열이 꽉 차 정확하게 판단할 수 없음)로 나뉩니다. 배열이 꽉 찼을 때 멀리 있는 적을 맞았다고 추측하지 않고 안전하게 막습니다. 기본 검사 배열은 64칸이고 매 프레임 새 배열을 만들지 않고 재사용합니다.

핵심 발췌, ShotgunCombat.cs 111~117행:

LastHit = query.Cast(guardOrigin.position, muzzle, range, hitLayers.value, spread, muzzleRadius);
PelletResolved?.Invoke(LastHit);
if (LastHit.Collider && LastHit.Kind == ShotHitKind.Hit)
{
    var receiver = LastHit.Collider.GetComponentInParent<IShotReceiver>();
    receiver?.ReceiveShot(LastHit);
}
  1. 한 산탄의 실제 충돌 결과를 계산합니다.
  2. 결과가 빗나감/막힘이어도 관심 있는 코드에 알립니다.
  3. 실제 명중한 경우에만 맞은 대상에게 알립니다.
  4. 충돌체 또는 부모에서 IShotReceiver 약속을 구현한 코드를 찾습니다.
  5. 그 코드가 있다면 해당 대상의 처리 방법을 실행합니다.

현재 팀 ThiefShotReceiver.cs 10~12행은 이 알림을 받아 TakeStun(stunDuration)을 호출합니다. 기본값은 1.5초입니다. 산탄 하나마다 수신될 수 있으므로 “한 번의 클릭은 정확히 한 번만 대상 효과를 호출한다”고 가정하면 안 됩니다. 새로운 체력·피해량을 추가할 때는 산탄별 피해인지 샷건 한 발당 피해인지 먼저 결정해야 합니다.

7.6 산탄 원과 모델 축

ShotSpreadRing은 현재 퍼짐 각도와 카메라 시야각을 읽어 화면 반지름을 계산합니다. 원이 산탄 방향을 결정하는 것이 아니라, 전투 코드가 결정한 각도를 따라 표시합니다. 조준 시 시야각도 줄어들므로 원의 화면 크기는 퍼짐 각도와 시야각 두 값의 영향을 받습니다.

현재 산탄은 완전한 난수 방식이 아닙니다. 네 방향을 균등하게 배치하고 ShotsFired에 따라 회전각과 반지름이 바뀌는 결정적인 패턴입니다. 따라서 “확률적으로 매번 독립 무작위 산탄”으로 문서화하면 실제 코드와 다릅니다. ShotgunCombat.cs 105~110행이 분포를 바꾸는 위치입니다.

현재 샷건 원본 모델의 총열은 로컬 -X 방향이고, 별도 muzzle 표시점은 +Z가 발사 방향입니다. ShotgunPose.Apply 107~117행은 이 모델 축을 보정합니다. 다른 무기 모델을 넣었는데 총이 옆으로 돌아가면 입력 코드보다 모델 축/총구 표시점/이 회전 보정을 먼저 확인해야 합니다.

8. SOLID 관점의 코드리뷰

이 표의 “확인된 구조”는 실제 소스에서 확인한 사실입니다. “검토 지점”은 지금 당장 재현한 오류가 아니라 향후 변경 시 주의할 위험입니다. 권장 구조가 있다고 해서 이번 문서 작성에서 자동으로 리팩터링하지 않습니다.

원칙 확인된 장점 현재 한계와 검토 지점 필요할 때의 개선 방향
S: 한 클래스의 책임을 좁힘 HandPolicy는 결정, ItemCarrier는 운반, HitscanQuery는 물리 조회, ItemHighlight는 표시, PickupReservation은 예약 복구 InteractionController는 대상 조회·손 조정·강조 연결을 함께 맡고 ItemInteractor는 등록/발견/저장/Enemy 연결을 함께 담당 대상 종류가 크게 늘어날 때만 대상 조회와 실행 연결을 별도 서비스로 나눔. 지금부터 빈 추상화만 늘리지 않음
O: 기존 코드를 덜 고치며 확장 IHighlightSource, IItemInventory, IPickupPort, IShotReceiver로 다른 구현을 연결 가능 ShotgunCombat은 구체적인 ShotgunEquipment/ShotgunPose에 의존. ShotgunPose는 현재 모델의 -X 축을 가정 다른 무기가 실제로 추가될 때 모델별 자세 어댑터나 작은 장비 계약 검토
L: 약속을 지키면 대체 가능 입력 공급자와 저장소를 주입할 수 있고 실패는 bool로 알림 사용자 저장소가 성공 반환 전에 저장하지 않거나 예외를 던지면 예약과 월드 상태가 어긋날 수 있음 TryAdd=false면 아무 변화 없음, true면 한 번 저장 완료라는 계약을 테스트로 고정

8.1 현재 코드에서 문서와 실행이 다른 부분

  1. 레이어 기반 F 자동 획득: 현재 ItemInteractor는 레이어 이름이 아니라 등록/ItemPickup/ThiefController로 대상을 찾습니다. 과거 설명을 그대로 믿고 Layer만 바꾸면 작동하지 않을 수 있습니다.
  2. 쥐 카운트 미구현이라는 주석: 현재 GetCaptured는 GameManager.OnRatCaught를 호출합니다. 실행 결과 설명은 “기절한 쥐 포획이 팀 라운드 카운트로 연결됨”이 맞습니다.
  3. UI 획득과 F 저장의 관계: UI 비행 연출 자체는 Hotbar 저장소가 아니며, F의 직접 저장과 별개입니다.
  4. 미사용으로 보이는 선언: RegisteredCommand에는 현재 정책이 내보내지 않는 Hold/Drop 값이 남아 있습니다. 코드에서 사용하지 않는 열거값과 파일 전체 미사용은 다른 문제입니다. 지우기 전 직렬화/외부 코드 참조까지 조사해야 하므로 이 문서에서 삭제하지 않습니다.

8.2 오류 재현 없이 단정하면 안 되는 부분

  • 스킨 강조의 이중 스케일 가능성은 현재 BakeMesh(true)와 변환 행렬의 조합에서 확인할 검토 지점입니다. 대상별 크기 비교가 필요합니다.
  • EnemyCaptured 수신자가 카운트를 다시 늘리는지 확인하지 않고 이중 카운트 버그가 있다고 단정하지 않습니다.
  • TryAdd나 피격 이벤트 수신자가 예외를 던졌을 때 중간 상태가 남을 수 있지만, 실제 수신자와 Console을 확인하기 전 현재 오류 원인으로 단정하지 않습니다.
  • ItemHighlight는 최근 대상의 Renderer 목록을 캐시합니다. 외형 교체 시 갱신 계약을 지켜야 합니다. 모든 동적 교체 사례가 새로 검증된 것은 아닙니다.

F09 인벤토리 데이터와 화면

인벤토리는 아이템을 기억하는 보관함, 핫바 UI는 그 보관함을 그리는 화면입니다. 화면에 그림이 없다고 곧바로 데이터가 사라진 것은 아닙니다. 반대로 덫 미리보기가 보인다고 실제 덫이 설치된 것도 아닙니다. 이 세 가지를 나누어 확인해야 합니다.

현재 연결

구성 실제 담당 하는 일
아이템 설명서 HotbarItemData.cs 이름, 아이콘, 설치할 프리팹을 보관하는 ScriptableObject
5칸 보관함 HotbarManager.cs 각 칸의 데이터와 선택 칸 관리, 빈칸 추가·사용, 휠 입력
보관함 화면 HotbarUI.cs 아이콘·이름·선택 테두리를 갱신
월드에서 줍기 ItemInteractor.cs, ItemPickup.cs F 대상과 거리 등을 검사하고 저장 성공 후 월드 물건 처리
덫 아이템 자료 TrapItem.asset itemId=jaw_trap, 표시 이름 덫, TrapIcon, Trap_Inventory 연결
설치할 실물 Trap_Inventory.prefab 기존 덫의 변형 프리팹. ItemPickup과 TrapPickup을 추가한 구성

HotbarManager, HotbarUI, HotbarItemData는 GameUI 쪽 기존 구현을 재사용·연결한 경로입니다. 플레이어 기능을 위해 만든 별도 두 번째 인벤토리가 아닙니다. 팀원의 보물 HUD와도 별개입니다. 보물 5개와 인벤토리 5칸은 숫자만 같고 서로 다른 자료입니다.

저장된 PlaytestScene01.unity의 Player 인스턴스는 readSelectionInput=1, readNumberKeys=0으로 덮어씁니다. 첫 슬롯의 데이터는 TrapItem입니다. 즉 첫 칸에 덫 1개를 들고 시작하고, 휠로 칸을 고르며, 숫자 1은 샷건에 남겨 둡니다. 코드 기본값 readNumberKeys=true만 보고 현재 씬도 숫자키로 선택한다고 설명하면 틀립니다. HotBar의 화면에는 아이콘·테두리·이름 연결 5묶음이 있고 buttons 배열은 비어 있습니다. 코드에는 버튼 선택 지원이 있어도 현재 저장된 화면에 클릭 버튼이 연결됐다고 볼 수는 없습니다.

보관함 코드 읽기

HotbarManager.TryAdd는 다음 순서로 동작합니다. 아래는 메서드 본문에서 가져온 실제 코드입니다.

slotIndex = -1;
if (item == null) return false;
slotIndex = FirstEmptySlot;
if (slotIndex < 0) return false;

slots[slotIndex] = item;
OnSlotChanged?.Invoke(slotIndex);
return true;
  1. -1은 아직 물건을 넣은 칸이 없다는 표시입니다.
  2. 넣을 데이터가 없거나 빈칸이 없으면 실패합니다. 기존 물건을 지우지 않습니다.
  3. 가장 왼쪽 빈칸에 같은 아이템 자료를 저장합니다. 같은 종류라도 한 칸에 여러 개 쌓는 구조는 아닙니다.
  4. OnSlotChanged는 “이 칸이 바뀌었어요”라는 알림입니다. UI가 이를 듣고 아이콘을 다시 그립니다. ?.는 듣는 쪽이 없어도 오류를 내지 않고 지나간다는 뜻입니다.

TryRemove(slotIndex, expected)는 칸 번호뿐 아니라 예상 아이템도 검사합니다. 설치를 누르는 동안 칸이 바뀌었는데 엉뚱한 물건을 소모하는 일을 막는 장치입니다. ConsumeSelected()는 선택 칸을 사용 처리하는 편의 함수입니다. 설치 쪽은 더 엄격한 TryRemove 경로를 사용합니다.

UI는 Start에서 HotbarManager.Instance를 찾아 알림을 구독합니다. RefreshSlot은 슬롯 데이터가 있으면 이름을 표시하고, 아이콘도 있으면 이미지를 켭니다. 테두리는 SelectedIndex에 맞춰 한 칸만 켭니다. 매 프레임 모든 아이콘을 다시 그리는 방식이 아닙니다.

F 획득과 손 상태

F 저장은 손에 총·다른 물건을 들고 있어도 그 손 상태를 유지합니다. 새 물건을 빈 인벤토리 칸에 넣는 행동입니다. 좌클릭 유지로 눈앞에 들고 다니는 기능과 다릅니다. 일반 대상의 발견·거리·벽 가림과 Enemy 조건은 상호작용 문서의 F06을 참고합니다.

덫에는 TrapPickup이 IItemPickupRule과 IItemPickupConsumption을 구현합니다. 인터페이스는 “이 물건에게 물어볼 수 있는 질문 목록”입니다.

public bool CanPickup => trap && !trap.IsUsed;
public bool ConsumeWorldInstance => true;

첫 줄은 덫 컴포넌트가 있고 아직 사용되지 않은 덫만 주울 수 있다는 뜻입니다. 두 번째 줄은 저장 성공 후 월드의 복제본을 없애야 한다는 뜻입니다. 사용된 덫을 다시 주워 무한 재사용하는 것을 막습니다. 프리팹 에셋 원본을 지우는 뜻은 아닙니다.

인벤토리를 수정할 때

  • 슬롯 수를 바꾸려면 HotbarManager의 배열뿐 아니라 HotbarUI의 슬롯 연결 수도 함께 맞춥니다. 현재 UI는 두 배열 길이가 같다는 전제로 값을 읽습니다.
  • 첫 아이템을 바꾸려면 해당 씬 Player 인스턴스의 HotbarManager slots[0] 연결을 바꿉니다. 원본 프리팹과 씬 덮어쓰기 중 어느 쪽을 편집하는지 먼저 확인합니다.
  • 아이콘이나 이름은 TrapItem 같은 HotbarItemData에서 수정합니다. 모델 자체를 바꾸는 곳은 placePrefab입니다.
  • UI만 교체할 때는 보관 데이터와 저장 메서드를 다시 만들지 말고 OnSlotChanged, OnSelectedChanged 알림을 새 UI가 듣게 연결합니다.
  • 이 구조에는 파일 저장·불러오기 기능이 없습니다. 게임을 껐다 켜도 재고를 기억하는 기능으로 설명하면 안 됩니다.

첫 줄은 유효하지 않은 위치, 다른 칸, 다른 슬롯으로 바뀌면 시간을 취소합니다. 다음 줄은 프레임 사이에 지난 시간을 누적하되 목표 시간보다 커지지 않게 합니다. 마지막은 시간이 찼을 때 딱 한 번 성공을 알립니다. 새 누름을 받은 프레임에는 시작 위치를 기록하며, 그 다음 유지 프레임부터 누적합니다. 그래서 표시상 1초를 기준으로 동작하되 프레임 단위의 작은 차이는 생깁니다.

격자와 장애물 판정

PlacementSurface.Failed는 다음 계산으로 위치를 고정합니다. 함수 이름은 실패 후보를 먼저 만드는 단계라는 뜻이며, 이후 검사를 통과하면 유효 후보가 됩니다.

var cell = new Vector2Int(Mathf.RoundToInt(point.x / cellSize),
                         Mathf.RoundToInt(point.z / cellSize));

격자 크기가 1이면 X=2.2, Z=4.7인 바닥 점은 대략 X=2, Z=5 칸 중심으로 맞춰집니다. 격자의 원점은 월드 (0,0,0)이고 설치 회전은 Quaternion.identity입니다. 맵의 회전이나 사용자 회전 입력에 따라 격자를 돌리는 기능은 없습니다.

검사는 아래 순서로 겹쳐 적용됩니다.

  1. 첫 충돌 확인: 카메라 광선에서 플레이어 자신과 일반 Trigger를 제외하고 가까운 충돌을 찾습니다. 벽을 맞았으면 그 뒤의 바닥을 유효 위치로 통과시키지 않습니다.
  2. 허용 바닥 확인: floors에 등록한 실제 Collider만 바닥으로 인정합니다. Item/Enemy 레이어를 붙이는 것과는 다른 목록입니다.
  3. 지지면 확인: 중앙과 네 모서리 아래에 바닥이 있어야 합니다. 최대 경사 약 15도, 다섯 지점 높이 차이는 0.08 이하입니다. 가장자리에서 덫 절반만 허공에 놓이지 않게 합니다.
  4. 거리·도달 경로: 플레이어 위치에서 Y 방향 0.65 올린 점을 기준으로 거리와 가림을 확인합니다. 화면에 보여도 멀거나 벽 뒤면 안 됩니다.
  5. 공간 확인: OverlapBoxNonAlloc으로 덫 폭과 높이의 공간을 확인합니다. 벽·기둥·기름통·매대처럼 Collider가 있는 장애물은 설치를 막습니다.
  6. 중복 덫 확인: Trigger뿐 아니라 기존 덫 Renderer의 bounds도 검사합니다. 발동 후 Trigger가 꺼졌더라도 보이는 덫에 겹쳐 설치하지 않도록 합니다.

NonAlloc은 검사 결과를 매번 새 배열로 만들지 않고 준비한 배열에 담는다는 뜻입니다. 현재 배열 용량은 128입니다. 꽉 찬 경우 “어쩌면 안전할 것”이라고 진행하지 않고 설치 불가로 처리합니다. Collider가 없는 장애물, Ignore Raycast 레이어로 제외한 물체까지 자동으로 감지하는 기능은 아닙니다.

미리보기와 실제 생성

PlacementFeedback은 원본 프리팹 전체를 생성하지 않습니다. Transform·MeshFilter·MeshRenderer를 복사해 외형만 표시합니다. Collider·덫 발동 스크립트가 없는 임시 오브젝트이므로 미리보기가 쥐를 잡지 않습니다. 임시 재질을 사용해 공유 재질의 색을 바꾸지 않으며 종료 때 해제합니다.

설치 가능은 반투명 초록, 불가능은 반투명 빨강입니다. 바닥 자체를 찾지 못하면 외형 대신 안내 문구만 남을 수 있습니다. 진행률은 유효한 바닥 후보에서 표시합니다. 현재 안내 문구의 “1초”는 문자열에 직접 쓰여 있으므로 holdSeconds를 바꾸면 안내도 함께 조정해야 합니다. 이것은 설정 확장 시 주의할 점이지 이번 문서 작업에서 수정한 내용은 아닙니다.

CompletePlacement는 시간이 찼다고 바로 재고를 지우지 않습니다. 카메라 위치, 같은 격자, 같은 슬롯, 같은 아이템을 다시 확인합니다. 복제본을 만든 뒤 TryRemove가 실패하면 방금 만든 복제본을 비활성화하고 제거합니다. 슬롯 변경 경쟁으로 물건만 잃거나 무료 덫이 남는 일을 줄입니다.

덫 발동과 라운드 수명

설치 프리팹은 기존 ConsumableJawTrap을 재사용합니다. TrapPickup.HandleTriggered는 전달받은 actor에 ThiefController가 있으면 TakeStun(Mathf.Max(.01f, trap.removeDelay))를 호출합니다. 덫을 밟았다고 이 연결부가 곧바로 쥐를 포획하거나 점수를 올리는 것은 아닙니다. 기절 뒤 F 포획은 기존 Enemy 경로가 처리합니다.

PlacedTrapLifetime은 이 TrapPlacement가 등록한 월드 복제본만 기억합니다. RoundClear, RoundResult, Win, Lose 및 다음 라운드 시작 시 남아 있는 설치물을 정리합니다. 시간 정지 상태에서도 표시와 충돌을 먼저 끄고 지연 없는 Destroy를 요청합니다. 시작부터 맵에 있던 덫, 인벤토리의 미사용 덫, Project 창의 프리팹 에셋을 지우는 목록이 아닙니다.

일반 게임 입력은 결과창 전 RoundClear 동안 일부 허용하지만 새 덫 설치는 Playing에서만 허용합니다. 설치물을 지운 뒤 결과 대기 중 다시 깔아서 남겨 버리는 일을 막습니다. GameManager 없는 독립 검사 환경에서는 설치를 허용하는 별도 경로가 있습니다.

3치즈 보상

정확한 조건

3치즈는 치즈 아이템 세 개를 인벤토리에 넣었다는 뜻이 아니라 라운드 방어 성적입니다. RoundResultUI.GetCheeseCount는 모든 보물을 지켰으면 3, 현재 기본 기준으로 3개 이상 남겼으면 2, 그보다 적으면 1을 표시합니다. 현재 씬은 보물 총 5개입니다.

라운드 종료 결과 치즈 표시 덫 보상
5개 중 5개 지킴 + 빈 인벤토리 있음 3 1개
5개 중 5개 지킴 + 5칸 모두 참 3 지급하지 않음. 나중에 재지급하지 않음
5개 중 3~4개 지킴 2 없음
5개 중 1~2개 지키고 클리어 1 없음
보물이 모두 사라져 패배 패배 경로 없음

보상 코드의 실제 조건은 result.treasuresTotal > 0 && result.IsPerfect이고, IsPerfect는 treasuresLost == 0입니다. 라운드 총 보물이 바뀌어도 “모두 지켰는가”가 기준입니다.

지급 시점과 중복 방지 코드

if (round <= lastProcessedRound) return;
lastProcessedRound = round;
if (perfect && inventory && trapItem)
    inventory.TryAdd(trapItem);

출처: TrapRoundReward.GrantOnce.

첫 줄은 같은 라운드 알림을 여러 번 받아도 중복 보상을 막습니다. 두 번째 줄은 이번 라운드를 처리했다고 표시합니다. 그 뒤 조건과 연결이 유효하면 가장 왼쪽 빈칸에 덫을 넣습니다. 처리 표시를 먼저 하기 때문에 가득 찬 경우, 연결이 없는 경우 모두 해당 라운드 보상을 나중에 자동 재시도하지 않습니다.

일반 라운드는 마지막 쥐 포획 → RoundClear → 현재 설정 1.5초 대기 → RoundResult/결과 알림 순서입니다. 보상은 그 결과 알림을 듣고 들어갑니다. 치즈 그림이 하나씩 나타나는 연출과는 별도로 진행합니다. 마지막 라운드는 GameManager가 곧바로 Win으로 가므로 TrapRoundReward가 Win 알림에서 결과 자료를 만들어 같은 조건으로 판단합니다.

보상이 안 보일 때 확인 순서

  1. 결과의 treasuresLost가 정말 0인지 봅니다. 화면의 치즈 연출 완료와 데이터 지급 시점은 다릅니다.
  2. HotbarManager의 5칸을 전부 확인합니다. 덫은 선택 칸이 아니라 가장 왼쪽 빈칸에 들어가며 선택은 자동으로 바꾸지 않습니다.
  3. Player의 TrapRoundReward가 활성 상태이고 inventory, trapItem 참조가 실제 사용 중인 보관함·TrapItem인지 확인합니다.
  4. 데이터는 추가됐는데 그림이 안 보이면 HotbarUI의 icon, label, border와 TrapItem.icon을 봅니다.
  5. GameManager/HotbarManager를 실행 중 교체하는 기능을 추가했다면 이벤트 연결을 확인합니다. 보상 연결은 OnEnable/Start에서 확인하며 매 Update 재연결하는 구조는 아닙니다. HotbarUI도 Start에서 한 번 연결합니다.

초기에는 F 토글이나 우클릭 집기를 요청했지만 현재 합의는 역할이 나뉩니다. 좌클릭 유지는 손 운반이고, F는 손 상태를 유지한 채 인벤토리로 새 물건을 보냅니다. 빈손·총·기존 물건 보유 중 어느 상태인지가 F 저장 뒤에도 유지됩니다. “총을 넣고 집기”는 이전 결정이며 최신 F 규칙으로 대체됐습니다. 덫이 선택된 상태의 설치 입력은 별도로 우선순위를 확인합니다.
